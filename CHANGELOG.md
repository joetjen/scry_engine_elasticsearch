# Changelog

## [Unreleased]

### Added

- Initial release: `Scry.Engine.Elasticsearch` -- a real `Scry.Core.EngineBehaviour` implementation over Elasticsearch, replacing `scry_search`'s own reference implementation (`Scry.Search.Executor`, a toy token-overlap relevance scorer) with genuine `SEARCH`/`relevance()` execution against a real full-text search engine. Closes the validation the roadmap already calls for: Elasticsearch is `search`'s own namesake reference language. Like `scry_logic`/`Scry.Logic.Executor` (replaced by `scry_engine_episteme`), `search` has no separate "engine" tier in its own reference form -- `Scry.Search.Executor` implements `Scry.Core.EngineBehaviour` directly rather than sitting on top of one, so this package does the same, translating the query into a real Elasticsearch Query DSL request (`Scry.Engine.Elasticsearch.QueryDsl`) via `req` (no actively-maintained Elasticsearch client fits this package's own runtime-configured `Conn.open/1` convention -- `snap`, the current best option, requires a compile-time `use Snap.Cluster` module in the *consuming* application).
  **Scoped deliberately to `SEARCH`/`relevance()`, not a general Elasticsearch-as-relational-store adapter**: `GROUP BY`/aggregates/`HAVING`/`DISTINCT`, and an ordinary (non-`SEARCH`) `WHERE` comparison, all depend on the same schema-level `NOT NULL` guarantee `scry_engine_exqlite`/`scry_engine_duckdbex`/`scry_engine_myxql` verify before trusting one -- confirmed directly that Elasticsearch has no equivalent to verify against at all (an index mapping declares a field's own type, never a presence/required guarantee). Rather than accept that gap silently, every construct needing it declines cleanly.
  **A real pagination-safety concern found and guarded against**: Elasticsearch's own default `size` is `10`, and `hits.total` is only a lower-bound estimate past 10,000 matches unless `track_total_hits: true` is set. `QueryDsl.compile/1` always sets an explicit `size` and always tracks the real total; `execute/3` declines with `{:query_error, {:result_window_exceeded, total}}` rather than silently returning a truncated page when no explicit `LIMIT` was given but more rows genuinely matched.
  **A real, confirmed architectural bug found and fixed during testing, not designed in up front**: `Scry.Core.QueryOps.run_flat/3` doesn't just apply projection -- it also re-evaluates `wheres` and re-applies `order_bys`/`limit`/`offset` generically (the mechanism `Scry.Search.Executor`'s own per-row scorer actually needs). Since Elasticsearch already fully and authoritatively evaluates and paginates the query server-side, the rewritten query handed to `run_flat/3` clears `wheres`/`order_bys`/`limit`/`offset` entirely rather than merely rewriting them -- left populated, each one either crashed outright (an unresolved `{:variant, {:search, ...}}` predicate reaching generic evaluation, or a bare `relevance()` order key core has no function for) or silently re-applied pagination on top of pagination that already happened (`LIMIT 1 OFFSET 1` against an already-offset single-row result returned nothing).
  **A real, confirmed Elasticsearch scoring quirk found and fixed**: wrapping a single top-level predicate in an extra `bool.must: [...]` layer is a semantic no-op for matching but a real scoring bug when the wrapped clause is itself a `bool.should` -- two documents that scored genuinely differently unwrapped came back with identical `_score` values once wrapped, turning `ORDER BY relevance()` into a tie broken by an arbitrary, direction-independent order. `QueryDsl` never adds that wrapper for a single top-level predicate. `minimum_should_match: 1` is always set explicitly on every `OR`-translated `bool.should`, confirmed directly against a real cluster to be necessary: the default flips from "at least one required" to "optional, score-only" the moment the query is nested inside a `bool` that also has a `must`/`filter` clause, a real trap for recursive combinator nesting.
